# Crypto wave 0 / batch 0: AVAES and AVAESCTR

Route verified: `type`; objective: `wrap`. Both public headers publish only
forward declarations. There are no public fields to wrap. Private storage stays
C-owned; the `ffibox` layout names the opaque FFI pointee, not a Rust-sized body.
Construction policies call the C allocators for the full aligned private bodies.
No shim or compiled C changed. No `Send`, `Sync`, or clone implementation added.

## Analysis and surface

Read aes.h, aes_internal.h, aes.c, x86/aes_init.c, aes_ctr.h/c, the
Wavefront records/dependency closure, and libavformat holders (crypto, MOV,
MOV CENC, SRTP, HLS/sample encryption, MXF). There were no Rust AES consumers.
Submitted both type records and all five constructor/initializer/free lifecycle
records through Wavefront `--update`.

AES stores only inline schedules/scratch and a process-lifetime C/assembly
function pointer. CTR stores inline AES, counters and offset, with no pointer
fields. Keys are copied, never retained. Contexts have exclusive holders; AES
holders free with av_free/av_freep, CTR holders with av_aes_ctr_free (av_free).
Neither type has a C cloning routine or field disposer. Borrowed handles are
provided by ffibox; their pointer seams stay crate-private.

AesFree delegates release to the existing Heap policy; AesCtrFree binds the C
free routine. Both release construction-phase storage without reading it. Safe
constructors promote storage only after initialization. Reinitialization requires
an exclusive handle. AES rejects invalid key lengths *before* FFI because C
otherwise changes rounds/crypt before returning EINVAL. CTR uses a fixed 16-byte
key and resets counter/partial-block state. Processing/IV symbols remain for
the subsequent symbol batch; equivalence tests use raw C observers only to
inspect states established by the safe lifecycle API.

### Pre-existing workspace gate blockers

The required full `cargo test --workspace` was run with stable Rust and sanitized
C libraries. Its only failing integration test is the existing `compile_fail`
snapshot gate: intfloat_mut_handle_sent_past_value and
intreadwrite_view_sent_past_bytes still reject with E0597, but the installed
rust-src adds a source excerpt absent from their checked-in stderr files.
Nightly additionally changes diagnostic wording in
bprint_append_with_storage_escapes and log_record_class_outlives_callback.

Running the complete nightly workspace with that snapshot test skipped passes
all runtime tests. Three unrelated compile-fail doctests in eval::ExprBox,
mem::Heap and opt::OptionRangesBox expect E0599 but receive E0308 (reference Clone
fallback). All four new AES/CTR doctests reject with their intended borrow errors.
These existing diagnostic expectations are outside this worklist and unchanged.
Initial full doctest invocation also needed RUSTDOCFLAGS to link the sanitizer
runtime; the corrected invocation confirms only those three diagnostic errors.

## Coverage

Focused `cargo +nightly test -p ffmpeg --lib --tests aes` with
CRUSTIFY_FFMPEG_VARIANT=coverage and RUSTFLAGS='-C instrument-coverage' passes.
With inline tests excluded, Rust AES covers 39/41 executable lines and CTR 18/20.
The four uncovered lines return InitializationFailed: current C always succeeds
for the valid lengths accepted by the safe API. Allocation failure is covered in
an isolated child process so av_max_alloc cannot interfere with other tests.

C lifecycle functions av_aes_alloc, av_aes_init, av_aes_ctr_alloc,
av_aes_ctr_init and av_aes_ctr_free each execute 100% of gcov-reported blocks.
The unsupported-key branch is intentionally unreachable through the safe API.
Whole-TU C line coverage: AES 103/143 (72.03%); CTR 39/59 (66.10%). Other uncovered
paths are processing/IV symbols outside this type batch and AES software fallback
processing bypassed by the host's AES-NI dispatch. Neither nondeterministic random
IV generation nor the C processing implementations are translated by this batch.

After the final rebase onto the CAST5/SHA/XTEA wave tip, workspace check and
ASan/UBSan runtime tests, all four workset doctests, TSan workset tests, both
exact BSan tests, Miri, and the target safety scan were rerun successfully.
